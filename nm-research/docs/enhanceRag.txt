================================================================================
NM RESEARCH — RAG SYSTEM RESTRUCTURE PROPOSAL
================================================================================
Date       : 2026-08-29
Based on   : NM RESEARCH — RAG SYSTEM ANALYSIS (2026-08-29)
Purpose    : Turn the existing analysis into a concrete, buildable redesign —
             architecture, guiding principles, and functional spec — that
             fixes the 2 confirmed bugs and 6 routing gaps without adding
             infrastructure the corpus doesn't need yet.
Bottom line: The current system is a lexical retriever wearing a semantic
             costume. It scores well (Hit@1 100%, MRR 1.000) because the
             score is a single entangled float that mixes cosine similarity,
             keyword overlap, and hand-tuned intent boosts. The fix is not a
             bigger model — it's decoupling the pipeline into stages that
             each have one job, a visible contract, and a safe default when
             evidence is thin.

--------------------------------------------------------------------------------
1. DIAGNOSIS — WHY THE CURRENT SYSTEM MISBEHAVES
--------------------------------------------------------------------------------
Old flow:  query -> ONE blended score -> answer
Every failure mode in the analysis traces back to this single design choice:

  B1 (greeting swallows question)
      -> "greeting" was an EXCLUSIVE gate instead of one flag among several.
  B2 (confidence isn't retrieval confidence)
      -> intentAdjustment can add +1.5 with zero lexical/semantic support,
         and calibrate() can't distinguish that from a well-supported hit.
  G1 (location/contact intents computed, never consumed)
      -> dead code that currently survives on lucky keyword overlap.
  G2 (human hand-off works by accident)
      -> rides on raw keyword overlap, not an explicit intent — untested.
  G3 (greeting+question is the leaky edge)
      -> same root cause as B1.
  G4 (quick-support vs contact-details near-tie)
      -> no resolution strategy for multi-topic or near-tied queries.
  G5 (special-intent regex runs pre-normalization)
      -> cosmetic today, but shows the special-intent layer sits OUTSIDE the
         normal signal pipeline instead of inside it.
  G6 (no tests pin greeting+question, hand-off, or edge singles)
      -> a symptom of intents not being required to have an owning test.

  L2 (hand-tuned constants everywhere) and L4 (single global threshold) are
  the same problem at the config level: nothing forces evidence type and
  evidence strength to stay distinguishable as the corpus grows.

Conclusion: the fix is architectural, not a patch per bug. Decouple query
understanding, evidence gathering, trust evaluation, and response composition
into four stages with explicit contracts between them.

--------------------------------------------------------------------------------
2. NEW ARCHITECTURE
--------------------------------------------------------------------------------
New flow:  query -> signals -> evidence -> gated decision -> answer

    ┌───────────────────────────┐
    │ STAGE 1 — QUERY            │
    │ UNDERSTANDING              │
    │                             │
    │ normalize -> tokenize ->    │
    │ detect ALL signals          │
    │ (greeting, thanks,          │
    │  hasQuestion, plan, intent, │
    │  human-handoff)             │
    │                             │
    │ Signals never short-circuit │
    │ retrieval by themselves.    │
    └──────────────┬──────────────┘
                   ▼
    ┌───────────────────────────┐
    │ STAGE 2 — EVIDENCE          │
    │ GATHERING                   │
    │                             │
    │ semantic: cosine similarity │
    │ lexical:  keyword/alias hit │
    │ routed:   explicit plan/    │
    │           intent name match │
    │                             │
    │ Kept as THREE separate      │
    │ numbers. Never blended into │
    │ one score at this stage.    │
    └──────────────┬──────────────┘
                   ▼
    ┌───────────────────────────┐
    │ STAGE 3 — TRUST GATE        │
    │                             │
    │ trustLevel decided from     │
    │ evidence TYPE mix, not just │
    │ magnitude (see section 4).  │
    │ This is where B2 is fixed.  │
    └──────────────┬──────────────┘
                   ▼
    ┌───────────────────────────┐
    │ STAGE 4 — RESPONSE          │
    │ COMPOSER                    │
    │                             │
    │ greeting+question -> both   │
    │ (greet in one line, then    │
    │ answer the remainder)       │
    │ low trust -> honest         │
    │ fallback + stated reason    │
    │ This is where B1 is fixed.  │
    └───────────────────────────┘

Everything still runs in-process, offline, deterministic, and free — no
vector DB, no model, no network call is introduced by this redesign. That
constraint is preserved deliberately; the analysis itself (L1, P6) says a
real embedding model is unnecessary at 29 docs and should wait until the
corpus grows past a few hundred chunks.

--------------------------------------------------------------------------------
3. GUIDING PRINCIPLES
--------------------------------------------------------------------------------
PRINCIPLE 1 — Signals compose, they don't gate exclusively.
  A signal (greeting, thanks, plan, intent) is a flag, never an early return
  on its own. The composer (Stage 4) decides how flags combine.
  Fixes: B1, G3, G5.

PRINCIPLE 2 — Confidence is a vote across evidence TYPES, not a sum of
  magnitudes.
  A score built from one strong evidence type (e.g. an intent-gate bonus with
  zero lexical or semantic support) must never present the same trust label
  as a score built from multiple corroborating evidence types.
  Fixes: B2, L4.

PRINCIPLE 3 — No declared signal without a consuming test.
  Every intent flag that is computed must have exactly one place that reads
  it, and a test that would fail if that consumption were removed. This
  turns "dead code that happens to work" into "code with an owner."
  Fixes: G1, G2, and generalizes G6 into a permanent CI rule instead of a
  one-off patch.

PRINCIPLE 4 — Constants are data, not folklore.
  Every hand-tuned number (blend weights, tanh center, confidence floor,
  intent boost magnitudes) lives in one named, documented config file, each
  constant with a comment pointing at the test that locks it. This doesn't
  change behavior today; it prevents the corpus from silently reordering
  rankings tomorrow (the real risk named in L2).

PRINCIPLE 5 — Near-ties and multi-topic queries get a strategy, not a guess.
  When the top two candidates are within a defined margin of each other, or
  when a query plausibly spans two topics, the composer says so instead of
  silently picking one. Cheapest version: a "did you mean X or Y" style
  disambiguation reusing data already computed. No new infrastructure.
  Fixes: G4.

PRINCIPLE 6 — Explain every answer with data you already computed.
  matchedKeywords is calculated today and never shown (L7). Once evidence
  types are separated (Principle 2), that same data becomes the one-line
  "matched: publications, membership" explanation shown to the user. This is
  what actually makes the system feel trustworthy — not a bigger model, a
  system that shows its work.

--------------------------------------------------------------------------------
4. FUNCTIONAL SPEC — KEY BEHAVIORS
--------------------------------------------------------------------------------
4.1 Signal detection (Stage 1)
    signals = {
      greeting: bool,
      thanks: bool,
      hasQuestion: bool,
      tokenCountAfterPhatic: int,
      plan: string | null,
      intent: string | null,
      humanHandoff: bool          // NEW — closes G2
    }
    Detection runs on the normalized string (closes G5's inconsistency),
    and greeting/thanks detection strips the phatic prefix before counting
    remaining tokens.

4.2 Evidence gathering (Stage 2)
    evidence = {
      semantic: number,   // cosine similarity, 0..1
      lexical:  number,   // keyword/alias overlap, as today
      routed:   boolean   // true only when the user's own words name the
                           // plan/intent explicitly (not inferred)
    }
    matchedKeywords continues to be computed here and passed forward
    unchanged in shape — only its destination changes (see 4.4).

4.3 Trust gate (Stage 3)
    trustLevel =
      "verified" if semantic > SEMANTIC_FLOOR AND lexical > 0
      "routed"   if routed AND (semantic > 0 OR lexical > 0)
      "matched"  if exactly one evidence type clears its floor
      "fallback" otherwise
    Concretely, this reclassifies today's "which plan has 2 publications"
    case: it keeps its plan-gate bonus and still answers correctly, but is
    now labeled "routed" instead of "verified" — because it has zero lexical
    or semantic support. The UI can style "routed" differently (e.g. a blue
    chip instead of green) without changing the underlying accuracy.

4.4 Response composition (Stage 4)
    - greeting/thanks AND remainder empty or phatic -> template only, as today.
    - greeting/thanks AND remainder has intent OR >= 3 tokens -> one-line
      greeting acknowledgment, followed immediately by the normal retrieval
      answer for the remainder. Closes B1.
    - Near-tie handling: if the top two candidate scores are within a fixed
      margin (e.g. 0.15 on the calibrated scale), the composer returns a
      short disambiguation ("Did you mean quick support or contact details?")
      instead of committing to the top-1 doc. Closes G4.
    - Every non-fallback answer appends a one-line "matched: <keywords>" or
      "matched via: <plan name>" explanation sourced directly from evidence
      computed in Stage 2. Closes L7.
    - Fallback answers explicitly state which evidence was missing (e.g.
      "I couldn't find a strong match for that") rather than a generic
      hand-off message, so a "fallback" and a near-miss "matched" don't read
      identically to the user.

4.5 Config centralization
    All hand-tuned constants (0.6/0.4 blend weights, tanh center 0.35,
    confidence floor 0.45, intent boost magnitudes such as +1.5/-0.4/-0.7,
    SEMANTIC_FLOOR, near-tie margin) move into a single scoring.config file.
    Each constant carries an inline comment naming the test file that would
    fail if it changed. No behavior changes from this step alone — it exists
    purely to make future corpus growth safe (L2).

4.6 Testing rule (enforced going forward)
    - Every new intent flag added to Stage 1 must ship with: (a) at least one
      consuming read in Stage 2 or 3, and (b) a golden test that exercises
      that consumption. A flag with no consuming test is a lint failure, not
      a warning.
    - Greeting+question, human-handoff, and near-tie disambiguation each get
      permanent golden cases in the eval set (closing G6), not one-off probes
      that get deleted after verification.

--------------------------------------------------------------------------------
5. BUILD ORDER (cheapest, highest-leverage first)
--------------------------------------------------------------------------------
  Step 1 — Signals compose instead of exclusive gate.
           Fixes B1, G3, G5. Cheap. Test-first: "hi what services do you
           offer?" must route to services-overview with a greeting prefix.

  Step 2 — Split evidence into semantic / lexical / routed; add trust ladder.
           Fixes B2, L4. Cheap. Test-first: "which plan has 2 publications"
           must land in trustLevel "routed", not "verified".

  Step 3 — Consume the dead intents: location -> global-presence boost,
           contact -> contact-details boost, new humanHandoff -> quick-
           support boost with an explicit test.
           Fixes G1, G2.

  Step 4 — Near-tie disambiguation using the existing top-2 scores.
           Fixes G4.

  Step 5 — Surface matchedKeywords as user-facing "matched: X, Y" microcopy.
           Fixes L7. Trivial effort, high perceived-quality gain.

  Step 6 — Centralize constants into scoring.config with per-constant test
           references.
           Fixes L2. Prevents silent regressions as the corpus grows.

  Step 7 — Confidence ladder surfaced in the UI (matched / routed / verified
           chips), built directly on Step 2's trustLevel.
           Fixes L4/L5's global-threshold problem.

  Step 8 — Durable feedback persistence (drain -> file or KV store instead
           of in-memory ring buffer).
           Fixes L5. Medium effort; do after the routing fixes, not before.

  Step 9 — Swap the hashed bag-of-features embedding for a trained/vector
           embedding model.
           Addresses L1/L6 — but ONLY once the corpus exceeds roughly a few
           hundred chunks. At 29 docs this is explicitly unnecessary; doing
           it now would add cost and non-determinism for no measurable gain.

--------------------------------------------------------------------------------
6. WHAT STAYS THE SAME (and why that's correct)
--------------------------------------------------------------------------------
  - Zero-cost, offline, in-process, deterministic execution: preserved.
  - The 42-case eval harness and its Hit@1/Hit@3/MRR floors: preserved,
    extended with the new golden cases from section 4.6.
  - The multi-turn session slot memory (30-min TTL, 12-turn cap, pronoun
    resolution): unchanged — it is already the highest-value conversational
    feature per the original analysis and needs no redesign.
  - Plan gateway comparison logic (2 publications -> Prime, etc.): unchanged
    in behavior, only reclassified in trust labeling (see 4.3).
  - Atomic, disciplined knowledge corpus with the "no orphan" test: unchanged.

--------------------------------------------------------------------------------
7. SUMMARY
--------------------------------------------------------------------------------
Nothing in this proposal adds new infrastructure. It takes the same
in-process, zero-cost, deterministic pipeline and splits one entangled score
into four stages — query understanding, evidence gathering, a trust gate,
and response composition — each with a single job and a visible contract.
That is what makes the result "highly user-friendly": not a UI overhaul, but
a system where a low-confidence answer says why it's unsure, a routed answer
is labeled differently from a verified one, and every declared signal has a
test proving someone actually uses it.
